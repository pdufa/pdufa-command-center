# Read-only scan schedule audit

`python scripts/audit_scan_schedule.py` compares saved metadata with the executable overnight launcher and its DST-aware admission script. It makes no network requests, dispatches no jobs, and writes no files. Exit 0 means consistent sources, exit 2 means stale saved metadata, and exit 3 means the operational sources could not be reconciled. Tests passing does not mean a stale-metadata finding has been resolved.

The live nightly clock is controlled by `.github/workflows/pdufa-nightly-pacific-start.yml` together with `scripts/nightly_start.py`. Commit `2b54596d` (PR #175) moved the entire guarded sequence to **20:00 America/Los_Angeles**, using the seasonal **03:00 UTC** / **04:00 UTC** primary triggers and existing duplicate/recovery protections. The script's admission start is also 20:00. The audit checks both seasonal primary slots; it does not claim a scheduled run actually started or completed.

The discrepancy is in saved metadata and documentation: `config/scan_234.json` still describes **22:00 Pacific**, older **05:00/06:00 UTC** triggers and an older recovery sweep, while README's historical scan-survey section also says 10 PM. The config is used by the local baseline input preflight and notification-policy tests. Its `clinical_source_schedule` clock fields are not read by the operational launcher/admission. Editing that saved label is not necessary to operate the current clock, and no schedule or metadata was changed as part of this investigation.

The current audit therefore reports `METADATA_DRIFT`, with `runtime_status: CONSISTENT`, effective start `20:00`, saved PDT/PST values `22:00`, exact differing cron entries, input checksums, and an explicit warning. This is a visible maintenance finding, not a silent success. Review and align the stale saved metadata/documentation separately after confirming the intended description. Any actual live schedule change still requires explicit approval.
